# Radeon 780M (Ryzen 7040 "Phoenix" / 8040 "Hawk Point")

Notes for running LLMs on the Radeon 780M iGPU under Linux. Each claim says
whether it was **measured** here or is **untested**. Results are in
[`../results/`](../results/); each run's `env.json` has the exact versions.

## The test machine (`fw13-7840u`)

- Framework Laptop 13 (AMD Ryzen 7040 Series), board revision A7, BIOS 03.20
- Ryzen 7 7840U: 8 cores / 16 threads, Zen 4 with AVX-512
- Radeon 780M: RDNA3, gfx1103, 12 CUs, PCI device `0x15bf` rev `0xc4`
- XDNA1 NPU (unused: see below)
- 32 GB DDR5, shared by CPU and GPU (unified memory; there is no VRAM)
- Ubuntu 26.04.1, kernel 7.0, Mesa 26.0.8 (RADV)

## Firmware and OS settings

- **BIOS GPU memory: "auto".** Framework's BIOS offers "auto" and "gaming". Auto reserves 512 MB for the GPU (`mem_info_vram_total`) and leaves 30.2 GiB visible to the OS. The GPU borrows system RAM through GTT anyway, so a large reserve only takes memory away from the OS. *Measured.*
- **GTT is capped at half of RAM by default: 15,438 MiB here.** That is the most the GPU can map, so a model plus its KV cache must fit in ~15 GiB to run fully on the GPU. A 17.7 GB model (Qwen3-30B-A3B UD-Q4_K_XL) can't, as things stand. *Measured (the limit); the effect on a >15 GiB model is untested.*
  - The usual fix is raising the TTM limit on the kernel command line, e.g. `ttm.pages_limit=6291456` (24 GiB in 4 KiB pages). *Untested here.* Leave headroom for the OS: running the system out of memory through the GPU can freeze it rather than fail cleanly (seen on a Strix Halo machine with the same unified-memory design).
- **Power:** results are recorded with `platform_profile=performance` on AC. `bench/run.sh` warns otherwise. On battery in the `balanced` profile, Qwen3-4B generated 26.7 tok/s against ~28 on AC in `performance`: a few percent, from runs that also differed in background load. *Measured, roughly.*

## Backends

- **Vulkan (RADV) works out of the box** and is what every result here uses unless it says otherwise. On Ubuntu/Debian: `sudo apt install libggml0-backend-vulkan` for the distro llama.cpp, or build upstream with `bench/build-llama-cpp.sh`. *Measured.*
- **ROCm/HIP:** gfx1103 is not on ROCm's supported list. Community reports use `HSA_OVERRIDE_GFX_VERSION=11.0.0`. Ubuntu packages a HIP backend (`libggml0-backend-hip`), and llama.cpp lists the 780M as `ROCm0` with it installed. Whether ROCm beats Vulkan on prompt processing is an open question. *Untested here.*
- **NPU (XDNA1):** there's no Linux runtime that runs LLMs on it. FastFlowLM supports XDNA2 (Strix and later) only. *Not usable.*

## llama.cpp

- **Upstream installs one `llama` binary** with subcommands (`llama bench`, `llama serve`, `llama cli`), where older and distro builds have `llama-bench`, `llama-server` and `llama-cli`. `bench/run.sh` handles both. *Measured (build 12020).*
- **Upstream needs `--spec-type` for speculative decoding.** It defaults to `none`, and a draft model passed with `-md` is then loaded and never used: decode speed equals running without it, and the response has no `draft_n` timing. Use `--spec-type draft-simple` for a separate draft model, and `draft-mtp` or `draft-eagle3` for a model's own draft head. The distro 8681 build drafts without the flag. *Measured.*
- **`-ub 512` (the default) can crash the GPU queue at long context.** A 2048-token prompt on top of 16k of context ran one GPU dispatch past amdgpu's compute timeout: `ring comp_1.1.0 timeout` in the kernel log, `vk::DeviceLostError` in llama.cpp. The driver recovers. `-ub 256` completes. *Measured (distro 8681).*
- **CPU: use 8 threads, not 16.** Hyperthreads compete for the same cores and memory bandwidth; 16 threads were 2-3x slower than 8. *Measured.*
- **Ollama's model files load in llama.cpp** when llama.cpp knows the architecture (Gemma 4 did, in 8681). Models Ollama runs on its own engine may not. *Measured for one model.*

## Framework Laptop 13 specifics

- **A failed USB-C expansion card stops charging silently.** The laptop ran on battery (discharging ~46 W) while plugged into a dead card. `cat /sys/class/power_supply/ACAD/online` shows `0`. *Measured.*

## Open questions

- MoE prompt processing on the 780M: no published numbers found (see [llama.cpp discussion #27519](https://github.com/ggml-org/llama.cpp/discussions/27519)).
- Vulkan against ROCm for prompt processing at depth.
- Raising GTT: what limit is safe, and whether 17-18 GB MoE models then run fully on the GPU.
- Several 780M machines as headless nodes: llama.cpp RPC (one model split across nodes; network-bound) against independent instances behind a router (throughput).
