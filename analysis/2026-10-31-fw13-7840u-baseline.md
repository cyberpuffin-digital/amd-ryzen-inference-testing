# Baseline: Radeon 780M, distro vs upstream llama.cpp (2026-10-31)

The first full runs on `fw13-7840u` (Framework Laptop 13, Ryzen 7 7840U,
Radeon 780M, 32 GB): nine models, each on Ubuntu's packaged llama.cpp
(build 8681) and on upstream (build 12020, commit `0ec4027a2`).

- Raw data: [`results/2026-10-31_fw13-7840u_b8681-distro/`](../results/2026-10-31_fw13-7840u_b8681-distro/) and [`results/2026-10-31_fw13-7840u_b12020/`](../results/2026-10-31_fw13-7840u_b12020/)
- Every number side by side: [`2026-10-31-fw13-7840u-distro-vs-upstream-tables.md`](2026-10-31-fw13-7840u-distro-vs-upstream-tables.md), generated by `analysis/compare.py`
- Hardware notes: [`../hardware/780m.md`](../hardware/780m.md)

## Conditions

Both runs: kernel 7.0.0-42, GTT raised to 24 GiB (`ttm.pages_limit=6291456`),
AC power, `performance` profile, Vulkan (RADV, Mesa 26.0.8), three
repetitions per test. Repetitions agreed to within 1%. Both runs recorded a
"system busy" warning (load average 1.2 and 2.3); the upstream run had the
higher load and was still faster, so load didn't flatter it. The runs were
hours apart, one after the other, not interleaved.

**What this can't tell you:** each build was run once, on one machine. Small
differences (a few percent) are within what a second run might move. The
speculative-decoding test is one prompt (writing a Python function) at
temperature 0, which favors drafting; expect less on varied chat.

## Findings

### 1. Upstream llama.cpp is much faster at reading prompts, and somewhat faster at generating

GPU prompt processing (pp512) went up **28-41%** on every model that ran on
both builds; generation (tg128) went up **3-16%**. The gap widens as context
fills on the MoE and larger models:

| model | pp2048 @ 16k, distro → upstream | tg64 @ 16k |
|---|--:|--:|
| Qwen3-30B-A3B-2507 | 73.9 → 126.5 (**+71%**) | 18.1 → 19.6 |
| Qwen3-8B | 77.0 → 139.7 (**+81%**) | 10.1 → 10.6 |
| gpt-oss-20b | 215.2 → 287.5 (+34%) | 22.2 → 23.8 |
| Gemma 4 26B-A4B | 210.2 → 259.3 (+23%) | 20.6 → 21.5 |

The CPU also gained: prompt processing on 8 threads rose 3-137% (most on the
smallest models; Gemma 4 26B-A4B barely moved); CPU generation barely moved.

### 2. The distro build can't load current Gemma 4 E2B/E4B files

ggml-org's `gemma-4-E2B-it` and `gemma-4-E4B-it` Q4_0 failed to load on build
8681: `missing tensor 'blk.24.attn_k.weight'`. These models share their KV
cache across later layers, and current conversions leave the unused tensors
out; build 8681 still expects them. An older conversion (Ollama's) loads on
8681. Upstream loads both.

### 3. On the distro build, mixed KV cache types collapse; upstream fixed it

With `-ctk f16 -ctv q8_0` (or the reverse), build 8681's prompt processing was
10-80x slower and generation 2.5-6x slower, on every model. Qwen3-8B ran at 4.1 / 2.7 t/s (pp / tg) against
161.8 / 12.4 with matched types. Upstream runs mixed types at near full speed.
Matched `q8_0/q8_0` also cost the distro build up to 28% of prompt speed on
most models; on upstream it is within a few percent of f16, and generation is
mostly slightly faster (a smaller cache to read). **On upstream, `-ctk q8_0 -ctv q8_0` halves KV memory at no
cost in these tests.**

### 4. Flash attention: always on

At 8k context, flash attention raised generation 11-86% on every model
(Qwen3-30B-A3B 15.1 → 25.3 t/s on upstream), and prompt processing on most.
Only Gemma 4's prompt processing was slightly slower with it (1-2%). No reason found to
turn it off.

### 5. Micro-batch 512 is slightly faster than 256 at 8k, on upstream

Upstream prompt processing at 8k was 0-13% faster with `-ub 512` (Qwen3-30B-A3B
185 → 210, gpt-oss-20b 358 → 404). These runs used `-ub 256` for the 16k sweep
because `-ub 512` at 16k crashed the GPU queue on build 8681 earlier (see the
hardware notes); whether upstream on kernel 7.0.0-42 survives `-ub 512` at 16k
is untested.

### 6. Speculative decoding: big wins with MTP and small drafts, losses on MoE targets

On upstream, decode speed with a draft against without:

| target | draft | type | alone → with draft | |
|---|---|---|--:|--:|
| Gemma 4 E4B | its MTP head | draft-mtp | 23.6 → **58.4** | **2.47x** |
| Gemma 4 26B-A4B | its MTP head | draft-mtp | 25.2 → **40.6** | **1.61x** |
| Qwen3-8B | Qwen3-0.6B | draft-simple | 16.6 → 30.4 | 1.83x |
| Qwen3-4B | Qwen3-0.6B | draft-simple | 28.6 → 39.9 | 1.40x |
| Qwen3-8B | Qwen3-1.7B | draft-simple | 16.6 → 20.5 | 1.23x |
| Qwen3-30B-A3B-2507 | Qwen3-0.6B | draft-simple | 35.0 → 26.3 | **0.75x** |
| gpt-oss-20b | its EAGLE3 head | draft-eagle3 | 28.6 → 22.0 | **0.77x** |

- The smaller draft won: 0.6B beat 1.7B for Qwen3-8B, despite similar
  acceptance. On this hardware the draft's own cost matters more than its
  accuracy.
- Drafting slowed both MoE targets tested with drafts. A plausible reason:
  checking several drafted tokens at once activates more experts than
  generating one, which erodes the reason MoE is fast here. The EAGLE3 head
  also had low acceptance (142 of 338). Gemma 26B-A4B is MoE too and gained
  from its MTP head, so this isn't universal. *Interpretation, not measured.*
- MTP and EAGLE3 need upstream: build 8681 has no `--spec-type`.

### 7. What runs well on this laptop

Generation speed at an empty context, upstream build:

| model | type | file | generation | with best draft | prompt (pp512) |
|---|---|--:|--:|--:|--:|
| Gemma 4 E4B | dense (per-layer embeddings) | 4.6 GB | 24.3 | **58.4** (MTP) | 612 |
| Gemma 4 26B-A4B | MoE, 4B active | 14.6 GB | 26.0 | **40.6** (MTP) | 493 |
| Qwen3-30B-A3B-2507 | MoE, 3B active | 17.7 GB | **36.1** | (drafting hurts) | 437 |
| gpt-oss-20b | MoE, 3.6B active | 12.1 GB | 29.3 | (drafting hurts) | 547 |
| Qwen3-8B | dense | 5.0 GB | 16.9 | 30.4 (0.6B) | 319 |
| Qwen3-4B | dense | 2.5 GB | 29.4 | 39.9 (0.6B) | 564 |
| Gemma 4 E2B | dense (per-layer embeddings) | 2.8 GB | 43.5 | – | 1162 |

The MoE models generate faster than dense Qwen3-8B while being far larger,
because each token reads only the active experts. Gemma 4 E-series also holds
its speed as context fills: E2B kept 86% of its generation speed at 16k
(43.8 → 37.5), where Qwen3-4B kept 51% (29.5 → 14.9).

## Suggested settings for a 780M (upstream build)

```bash
llama serve -m <model> -dev Vulkan0 -ngl 99 -fa on -ctk q8_0 -ctv q8_0 -ub 256
# Gemma 4 with its MTP head:
#   -md mtp-<model>.gguf --spec-type draft-mtp -ngld 99 -devd Vulkan0
# Qwen3 dense with a small draft:
#   -md Qwen3-0.6B-Q8_0.gguf --spec-type draft-simple -ngld 99 -devd Vulkan0
```

`-ub 512` is a few percent faster for prompts at moderate context; keep 256
where long contexts are expected until 512 at 16k is retested.
